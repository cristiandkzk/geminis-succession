# Progress update — September 21, 2026

[Español](2026-09-21.md) · **English**

**In one line:** the succession mechanism does not only change parameters. It can also change the
**signature scheme** (and the **hash function**) of a running chain, and the new signatures are actually
verified by the same frozen machine.

Each item below says which repository it lives in. `geminis-succession` is this one; `Geminis` is the main
repository, where the research and the reference implementation live.

**A note on the starting signature.** The reference genesis starts from a classical signature (Ed25519) on
purpose, to demonstrate a migration. The starting signature is a genesis parameter, not a position about what a
chain should use: the paper's own choice for a chain born new is still ML-DSA-44 (§10.1).

## Built

- **The signature changes too, with real signatures** (`Geminis`, [Test 9](https://github.com/cristiandkzk/Geminis/tree/main/test9-ed25519-a-mldsa)).
  A chain that accepts only Ed25519 reaches a deterministic trigger and, without restarting and without moving its
  root, also accepts ML-DSA-44. In each generation a signature is first admitted by the formats that generation
  knows, then verified inside the frozen RV32IM machine under that generation's step and page ceilings, and every
  verdict is cross-checked against native verification. A signature from the old generation stays valid.
- **The same change for Ethereum's own signature** (`Geminis`, [Test 10](https://github.com/cristiandkzk/Geminis/tree/main/test10-secp256k1-a-mldsa)).
  secp256k1 (the ECDSA that Ethereum accounts use today) → ML-DSA-44, checked against a well-known Ethereum
  address (private key 1 → `0x7e5f…5bdf`; `ecrecover` run on the machine recovers the same address) and enforcing
  EIP-2's low-`s` rule.
- **Hash and signature succeed independently, in any order** (`Geminis`,
  [results](https://github.com/cristiandkzk/Geminis/blob/main/geminis/sucesion/RESULTS-HASH-Y-FIRMA.md)).
  BLAKE2s → SHA-3 and Ed25519 → ML-DSA-44, in three orders (hash first, signature first, both at once): same final
  state, lineage verifies end to end, genesis root unchanged. Each checkpoint is computed with its ancestor's hash,
  so verifying a step never requires trusting the primitive it introduces.
- **Signature measured, not assumed** (`Geminis`, [Test 8](https://github.com/cristiandkzk/Geminis/tree/main/test8-ed25519)).
  "Ed25519 is more efficient" turned out to be 1.02–1.11× fewer steps than ML-DSA-44 on this machine, about 1.3× in
  capacity per block.
- **This repository (pushed):** the hash function now succeeds inside the chain (SHA-256 → SHA-3), and the signature
  canary is no longer a counter: spending it requires a valid signature from a weak instance derived from a public
  seed. 142 Python and 20 Rust criteria pass (commits `aef9ce9`, `c3d4512`, `41eb7ad`).

## Learned

- **Ethereum has not chosen ML-DSA-44.** According to [ethereum.org](https://ethereum.org/roadmap/security/quantum-resistance/)
  and [pq.ethereum.org](https://pq.ethereum.org/), accounts would move through account abstraction (EIP-8141, under
  consideration for the Hegotá fork) with Falcon, Dilithium (ML-DSA) and SPHINCS+ as candidates, and validators
  would move to leanXMSS (hash-based) through hard forks, with a 2029 target. ML-DSA is one candidate among several.
- **Ethereum's signature is the most expensive in this machine.** Steps per verification: Ed25519 3.28 M,
  ML-DSA-44 3.32 M, secp256k1 5.67 M. `ecrecover` costs 11.33 M and does not fit under the initial 7 M-step ceiling.
  Moving to ML-DSA-44 would give capacity back; what grows is size, about 38×.
- **Independent mechanisms are not independent security.** Ed25519 hashes with SHA-2 and ML-DSA with Keccak, so
  once both transitions have happened the chain hash shares a core with a signature. The check reports the step
  where that appears; it does not block it. We declare it as a limit rather than hide it. It also made us move the
  main repository's genesis hash from SHA-256 to BLAKE2s.
- **We caught our own mistakes.** ML-DSA-87 is not a successor, only a cost level measured in an earlier test. A
  devnet figure in the main repository was stale (3.01% of the block; the corrected model gives 9.62%, and 4.97% with
  the new hash). And no test pinned a hash, so changing the hash function had passed silently: it is pinned now.

## Limits, declared

- The node does not route signatures to the machine yet: the tests do. The synthetic state has no accounts.
- The main repository's signature canary is still a counter; this repository's is verified.
- One implementation per primitive, reference crates, x86-64 only.
- What comes after ML-DSA-44 is open. The paper says the successor is delivered as bytecode and accepted by a
  gauntlet; that path is not built.
- The demo in this repository still uses SHA-256 as the genesis hash. The main repository has moved on to BLAKE2s.
